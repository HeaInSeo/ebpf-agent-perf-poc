# R001 — 선택적 eBPF 계측의 비용·정보 가치와 1차 의견

2026-10-22 UTC. **작성자의 1차 의견: 현재 가드레일 전체에 eBPF를 상시 추가하는 것은 권하지 않는다. 원인 진단이 필요한 경로의 선택적 도구로 검토할 가치는 남아 있다.**

이 의견의 핵심 근거는 추가 계측 비용이 확인된 데 비해, 그 비용에 대응하는 더 나은 구현 선택이나 진단이 아직 입증되지 않았다는 것이다. 이번 실험은 그 판단의 근거를 보강한 첫 단계다. 전체 PoC의 성공 판정이나 eBPF 전반의 무용성 판정으로 확대하지 않는다.

## 연구 질문 / 범위

- 질문: 기존 Go 실행 증거에 하나의 eBPF 수집기를 추가할 때 무엇이 더 보이고, 자원을 얼마나 더 쓰는가?
- [사전 고정 프로토콜](R001-PROTOCOL.md). 두 실행 모두 소스 `24a6e4a3ca48a53d0b16bf22882c0a9793c60623`을 사용했다.
- 기존 `iobench`의 명시적 read/write 복사 동작을 분리한 `costbench`에서 A=32KiB, B=64KiB 재사용 버퍼를 비교했다. 다른 아키텍처 두 개를 비교한 실험은 아니다.
- 컨텍스트: 캐시된 일반 파일의 순차 복사, 처리 시간 우선, 작업자 1개, GOMAXPROCS=2, 복사 버퍼 예산 128KiB. 두 후보 모두 이 버퍼 예산 안에 있다. 프로세스 전체 메모리 한도가 128KiB라는 뜻은 아니다.
- 수집 조건은 128KiB 파일×2048회와 16MiB 파일×32회. 별도 검증 조건은 192KiB×2304회와 12MiB×48회. 각 조건·후보·모드당 12회, 고정 시드로 순서를 섞었다.
- 모드는 native / Go CPU pprof+runtime trace / 동일 Go 계측+eBPF다. Go 비교 조건에 프로파일과 trace를 실제로 제공했다.
- Go만의 선택을 고정한 뒤 별도 조건을 실행했다. 기능 동등성·정확한 계측·잡음 확인과 비용 측정이 범위다. 독립 AI 평가, 실제 제품 결함 발견, 자동 코드 변경은 이번에 검증하지 않았다. E006/G6는 계속 OPEN이다.

- 복사 구간 자체의 추가 지연은 조건별 중앙 비율 기준 약 **11–63%**였다. 작은 절대 시간의 비율이므로, 이것을 모든 프로그램의 감속률로 일반화하면 안 된다. 두 모드의 중앙 복사 시간 차이는 약 **5–41ms**다.
- 수집 1회 전체 명령의 추가 시간은 약 **0.57–0.74초**였다. 매번 수집기를 시작한 방식의 결과다. 연결 준비는 약 0.20초(Intel)/0.27초(AMD)였고, 나머지에는 수집기 종료·정리와 실행 지연도 포함된다.
- 수집기 최대 RSS의 조건별 중앙값은 약 **101.4–101.6MiB**였다. 대상 Go 프로세스 최대 RSS는 Go 계측과 Go+eBPF 모두 약 9MiB 수준이었다. 수집기 RSS와 대상 RSS를 합산한 동시 최대 메모리를 측정한 것은 아니다.
- Go pprof+trace도 자체 비용이 있다. [summary JSON](r001-evidence/39781417174/summary.json)의 `go_over_native_hot_ratio`와 두 번째 실행의 같은 항목에 별도로 보존했다. eBPF의 추가 비용은 동일한 Go 계측 조건끼리 비교했다.
- 저장량은 Go 프로파일이 대부분이다. 실행 1의 수집 결과는 Go 약 7.94MB, Go+eBPF 약 7.93MB; 실행 2는 약 7.90/7.93MB였다. 이 실험에서 eBPF 때문에 저장량이 크게 증가했다고 말할 근거는 없다.
- 전체 job 105초는 테스트·모든 비교·프로파일 해석·보존을 포함한 실험 시간이다. 이를 eBPF만의 비용이나 기존 repo 전체 CI 비용으로 계산하면 안 된다.

커널·이미지가 같아도 CPU가 달랐고, 비용 비율도 달랐다. 각 실행 안에서는 같은 CPU에서 모드를 비교했으나 두 실행을 한 환경의 단일 정밀 추정치로 합치지 않는다. bpftrace를 매번 시작한 비용을 미리 컴파일한 수집기나 상주 수집기의 비용으로 적용하지 않는다. 해당 경로의 비용은 측정하지 않았다.

## 추가 정보가 실제 판단에 기여했는가

### Go 자료만으로 확인한 내용

풀링한 Go CPU 프로파일은 read/write 시스템 호출 경로가 주요 CPU 소비처임을 보여줬다. 예를 들어 실행 1의 큰 파일·32KiB 조건은 `internal/runtime/syscall.Syscall6`가 flat CPU의 84.71%였고, Read/Write 경로도 스택에서 구분됐다. runtime trace에서 만든 syscall/scheduler/sync 프로파일도 함께 제공했다. 개별 실행은 짧으며, 풀링한 CPU 샘플 시간은 조건별 0.28–1.57초다. 세밀한 모든 원인을 식별할 정도의 프로파일이라고 과장하지 않는다.

소스에서 버퍼 크기, 재사용 방식, read/write 루프도 이미 확인할 수 있었다. 따라서 B의 호출 횟수가 줄어들 것이라는 가설은 eBPF가 있어야만 세울 수 있는 가설은 아니었다.

### eBPF가 실제로 더 제공한 내용

- 대상 TGID와 실제 입출력 FD로 한정한 정확한 read/write 호출 수, 실제 반환 바이트, 오류 수, syscall별 누적 경과 시간을 얻었다. 96회 정식 계측과 4개 제어 모두 원시 카운터를 다시 계산해 일치했다.
- 예를 들어 큰 파일 512MiB 복사에서 A는 read 16,416/write 16,384회, B는 read 8,224/write 8,192회였다. 두 후보 모두 read/write 각각 536,870,912바이트였고 오류는 0이었다. EOF read가 포함돼 read가 write보다 많다.
- 이 수치는 Go CPU 샘플보다 정확한 **실행 확인과 시간 분해**다. 그러나 기존 소스·프로파일로 설명되지 않던 결함을 발견하거나, 바뀐 진단을 독립 검증한 사례는 이번에 나오지 않았다.
- syscall 누적 경과 시간은 계측이 붙은 실행의 값이다. Go runtime trace의 blocking profile과 정의가 다르며, 두 숫자를 같은 지연 시간으로 취급하지 않는다. 계측 없는 실행의 원래 syscall 시간을 복원한 값도 아니다.

### 구현 선택

B/A가 작을수록 B가 빠르다. 95% 구간 전체가 0.95 미만일 때만 B, 1.05 초과일 때만 A, 그 외에는 ABSTAIN으로 고정했다. 아래 선택은 **수집한 native 시간에 적용한 고정 규칙**이며 AI 평가자의 결정이 아니다.

| 실행 | 입력 | 계측 없는 수집 구간 B/A [95% CI] | 봉인한 Go 규칙 선택 | 별도 조건 B/A [95% CI] |
|---|---|---|---|---|
| 1 | small | 0.800 [0.785, 0.816] | B | 0.805 [0.799, 0.820] |
| 1 | large | 0.918 [0.764, 1.038] | ABSTAIN | 0.809 [0.735, 0.902] |
| 2 | small | 0.761 [0.745, 0.778] | B | 0.792 [0.739, 0.844] |
| 2 | large | 0.790 [0.748, 0.845] | B | 0.783 [0.771, 0.820] |

Go 규칙은 네 조합 중 세 조합에서 B를 선택했고, 한 조합에서는 잡음 때문에 보류했다. 별도 검증에서는 네 조합 모두 B가 빠른 것으로 확인됐다. 보류를 오답으로 바꾸거나, 커널 호출 수가 적다는 이유만으로 강제로 선택하지 않았다. 호출 수 감소는 처리 시간 목표의 보증이 아니다.

두 정보 조건에 동일한 timing rule을 쓰므로, 이 표만으로 Go+eBPF가 독립 평가에서 같은 선택을 했다는 실증 결과를 만들 수 없다. **이번에 수행한 것은 정보·비용 비교이며, 독립 AI의 추가 선택·진단 개선은 미검증이다.** 첫 실행의 보류를 eBPF가 해결했다는 근거도 없다.

## 작성자의 1차 의견과 의사결정 제안

**지금 내가 결정한다면, 기존 가드레일 전체에 eBPF를 상시 추가하는 작업은 보류하겠다. 기존 Go 프로파일·trace와 요구사항 기반 품질 기준을 우선 활용하고, eBPF는 특정 원인 진단을 위한 수동 선택 경로로만 남기겠다.**

이유는 다음과 같다.

1. 추가 계측의 정확성과 비용은 관측했지만, 더 나은 구현 선택이나 새로운 결함 발견이라는 이득은 아직 입증하지 못했다. 먼저 도입하고 효과가 있을 것으로 기대하기에는 증거가 부족하다.
2. 실제 추가 시간이 1회 약 0.6초인 것은 절대적으로 큰 비용만은 아니다. 도입 보류의 핵심은 그 시간이 감당 불가능해서가 아니라, 현재 얻는 정보가 기존 증거와 상당 부분 겹치기 때문이다.
3. 계측 자체가 복사 시간을 바꾸므로 계측 수치로 후보를 바로 순위 매기면 오판할 수 있다. 성능 판정은 계측 없는 검증과 연결해야 한다.
4. 품질 기준과 컨텍스트를 정하는 일에는 여전히 제품 요구·계약·워크로드·실패 의미가 필요하다. 정확한 커널 카운터가 그 기준을 자동으로 만들어 주는 가능성은 이번에 검증하지 않았다.

이번 결과가 지지하는 범위는 **선택적 실행 관측의 기술적 가능성**이다. **범용 코드 품질 향상이나 투자 대비 효과는 미입증**이다. 독립 AI 평가도 하지 않았으므로, 가능성이 없다고 단정할 근거도 갖추지 못했다.

후속 투자를 결정한다면, 기존 Go 자료로 원인이 해결되지 않는 실제 문제 하나를 먼저 고르는 것이 좋겠다. 그때는 I/O 대기·재전송·자식 프로세스 잔존처럼 제품 문제와 연결되는 구체적 가설을 두고, 더 간단한 OS 도구와 eBPF, 충분한 Go 증거를 독립 평가해야 한다. 같은 단순 복사 실험을 더 반복하거나 언어별 수집기를 늘리는 일을 다음 목표로 권하지 않는다. 후속 작업은 사용자의 판단에 맡기며 자동으로 시작하지 않았다.

## 증거 검증·재실행·반증

- [전체 증거 안내](r001-evidence/README.md), [추가 감사 결과](r001-evidence/AUDIT.json).
- 원본 ZIP 두 개의 SHA256이 GitHub artifact digest와 일치했고, 각 내부 manifest 1,276개 파일, 합계 **2,552개**의 해시를 검증했다. 별도 감사 스크립트로 raw stdout, 카운터, 바이트, 관측 수, 통계 중앙값과 봉인 순서를 다시 확인했다. 같은 작성자가 수행한 재계산이며 별도 사람/에이전트의 독립 검토 완료가 아니다.
- 수집 소스·프로토콜과 원시 Go 프로파일/trace가 보존돼 있다. 독립 검토자는 ZIP을 풀고 `python3 experiments/value-cost/audit.py <run1-dir> <run2-dir>`로 검증할 수 있다.
- 같은 소스를 별도 runner에서 실행하거나, 소스와 Go 자료만으로 동일한 진단이 가능한지 확인하거나, eBPF 자료가 있을 때만 가능한 올바른 판단을 제시하면 이 1차 의견을 반증·수정할 수 있다.
- 코드 재현은 소스 SHA를 checkout하고 `value-cost.yml`과 동일한 명령을 사용한다. 현재 main의 workflow는 수동 실행만 허용한다. 외부 upstream, Notion 가드레일 및 다른 repo의 workflow는 변경하지 않았다.
